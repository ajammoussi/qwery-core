# Benchmark Handoff

This document explains the complete benchmark architecture, the metrics implemented, the design decisions behind them, and the results observed so far. It is intended as a reference for writing up the evaluation methodology in the official report.

See `README.md` for setup and runner commands.

---

## Architecture Overview

### Data flow

```
data/sessions/{db}/{type}/{id}.json
        │  scripted user turns only
        ▼
  pnpm run:qwery-default          ← runs the real agent turn by turn
        │  stores full turn trace + compaction events
        ▼
data/results/{method}/{mode}/{db}/{type}/{id}.json   (BenchmarkResult)
        │
        ├── pnpm extract          ← aggregates inline metrics into reports
        │         ▼
        │   data/reports/benchmark-report-{method}-{mode}-{date}.json
        │
        └── pnpm verify:consistency  ← post-processing judge pass
                  │  re-runs agent with stripped context
                  │  calls Gemini as quality judge
                  │  --patch writes back to BenchmarkResult
                  ▼
        metrics.geminiJudge + metrics.queryConsistencyRate populated
```

### Key entities

- **BenchmarkSession** (`data/sessions/`) — the test case: scripted user turns, annotations (which turns establish filters, which are anaphoric references, etc.), persisted corrections, and the compression boundary turn number.
- **BenchmarkResult** (`data/results/`) — the ground truth output: every turn's agent response, tool calls, token counts, timing, compaction events, and computed metrics. This is the permanent record.
- **Reports** (`data/reports/`) — aggregated summaries generated by `extract-results.ts`. Derived from result files; safe to regenerate at any time.

## Metrics: Design Rationale

### Why two categories of metrics?

Inline metrics (computed from stored turn data) can be regenerated from any result file without re-running the agent. They measure structural properties: did SQL succeed, were table references valid, how much latency did compaction add.

Post-processing metrics require external resources — a live database for SQL re-execution and Gemini for quality judgment. They are more expensive to produce but capture *what matters most*: does the compression strategy actually preserve the analytical context a user has built up?

The separation is deliberate: a strategy could have excellent inline metrics (fast, valid SQL, low latency) while still silently losing filter context after compaction.

### Inline metrics

| Metric | Field | Rationale |
|--------|-------|-----------|
| SQL Validity Rate | `sqlValidityRate` | Compression should not cause the model to hallucinate syntax. Differentiates strategies that corrupt the model's understanding of the schema vs. those that merely lose context. |
| Schema Grounding Rate | `schemaGroundingRate` | The model should only reference tables that appeared in `getSchema` output. Captures hallucinated table names — a hard failure that wouldn't show up in a row-count check. |
| Total Compaction Latency | `totalCompactionLatencyMs` | Sums ALL compaction events, not just the first. Some strategies compact multiple times. |
| Compaction Overhead % | `compactionOverheadPct` | `totalCompactionLatencyMs / totalResponseTimeMs × 100`. Makes latency comparable across sessions of different lengths. |
| Filter Persistence Rate | `filterPersistenceRate` | Keyword-based check: do established corrections appear in post-compaction SQL? Coarse but fast. The Gemini judge is the fine-grained version of this. |
| Reference Resolution Accuracy | `referenceResolutionAccuracy` | Checks anaphoric references and callbacks that cross the compression boundary. |
| Tool Success Rate | `toolSuccessRate` | % tool calls with `success: true`. Catches regressions where compaction causes the agent to call tools incorrectly. |

All SQL metrics (`sqlValidityRate`, `schemaGroundingRate`) run only on `toolInput.query` strings — never on free-text agent responses — to avoid false positives from phrases like "from our perspective" matching SQL keywords.

### Post-processing metrics: the compression faithfulness test

The core test: strip the pre-compaction conversation history, inject only the compressed summary, re-run the benchmark model on a post-compaction turn, and measure how close the output is to what the model produced with full context.

**Why this matters**: two strategies might produce similar token savings but differ dramatically in what they preserve. A summary that faithfully retains filters and corrections will produce equivalent SQL; one that loses them will silently produce wrong answers.

**Re-execution flow** (per sampled turn):
1. Find the first compaction event's `summaryText`
2. Build synthetic context: `[assistant: <summary>, user: <turn message>]`
3. Run the benchmark model with only this context
4. Extract SQL from the re-run, execute against the live database
5. Compare row counts against the stored reference SQL

**Why row counts, not exact SQL**: SQL exact match is too strict — minor alias differences, column ordering, or whitespace changes produce false negatives for semantically equivalent queries. Row counts confirm the query returns the right data.

## The Gemini Judge: Design Rationale

### Why not just row counts?

Row counts catch outright wrong answers but miss subtle context failures:
- A query that aggregates correctly but applies the wrong fiscal year definition
- A response that references the right table but ignores a stated exclusion filter
- A turn where the agent simply doesn't run any SQL but answers from the (stale) summary

A single 0–10 score captures some of this but loses *what failed* — making it hard to distinguish strategies or understand where to improve.

### Multi-dimension rubric (Option A) + failure tags (Option D)

Gemini is asked to score four specific dimensions (0–5 each) and tag any failure categories.

**Dimensions:**

| Dimension | What it measures |
|-----------|-----------------|
| `filterPersistence` | Did the re-run apply all established filters and exclusion rules? (e.g., fiscal year definition, order priority exclusions) |
| `entityContinuity` | Did the re-run reference the correct entities? (e.g., correct date ranges, named groups, segment labels) |
| `correctionPersistence` | Were explicit user corrections from earlier turns respected? (e.g., "exclude that segment", "use July–June fiscal year") |
| `analyticalThread` | Does the re-run understand what is being investigated — the trend, comparison, or root cause established in the conversation? |

Each dimension gets a score 0–5 with a one-sentence explanation. Overall = `avg(4 dims) × 2`, normalised to 0–10.

**Failure categories** (tagged alongside the scores):

| Tag | Meaning |
|-----|---------|
| `filter_drift` | An established filter was omitted or applied incorrectly |
| `entity_confusion` | Wrong entity, date range, or category referenced |
| `baseline_loss` | A prior baseline value or analytical reference was not retained |
| `correction_ignored` | An explicit user correction from an earlier turn was not applied |

The tags make cross-session analysis tractable: instead of reading individual turn reasoning, you can look at which failure modes dominate a given strategy.

**Why Gemini specifically**: The judge needs to see the complete original conversation (ground truth) plus the compressed summary plus the re-run response — all at once. Gemini's 1M-token context window makes this feasible for long sessions. The benchmark model runs with the *stripped* context; Gemini runs with *everything*.

### Limitations of the judge

- Scores are per-turn samples, not full sessions. 5 sampled turns is a heuristic.
- Gemini itself can be inconsistent across runs (different score on the same input at different times). For final report figures, increase `--sample` and consider averaging two independent judge passes.
- Turns without SQL (purely analytical responses) are harder to evaluate — Gemini may score them higher or lower depending on how much analytical language it deems equivalent.

## Observed Results (2026-05-27)

Only `qwery-default/plain/tpch/dcs/tpch-dcs-001` has been run through the full pipeline so far.

### Inline metrics

| Method | SQL Validity | Schema Grounding | Compaction Latency | Overhead |
|--------|-------------|------------------|--------------------|----------|
| baseline-no-compression / plain | 90.6% | 81.3% | — | — |
| qwery-default / plain | 93.3% | 93.3% | 19,318 ms | 2.1% |
| qwery-default / 4zone | n/a (0 tool calls recorded) | n/a | 15,149 ms | 1.6% |

Note: The 4zone result has 0 tool calls recorded — likely a logging issue in the 4zone runner path, not an actual agent behavior problem.

### Post-processing metrics (qwery-default / plain / tpch-dcs-001, 5 sampled turns)

| Metric | Value |
|--------|-------|
| Row-count match rate | 60% (first run) / 0% (second run — DB down) |
| **Gemini context score** | **6.67 / 10** |
| ↳ filter_persistence | **2.00 / 5** |
| ↳ entity_continuity | **5.00 / 5** |
| ↳ correction_persistence | **1.67 / 5** |
| ↳ analytical_thread | **4.67 / 5** |
| Dominant failure categories | `filter_drift` (2 turns), `correction_ignored` (2 turns) |

### Interpretation

Entity recall and analytical intent are preserved well by `qwery-default`. The weak spots are filter and correction persistence — exactly the dimensions most sensitive to lossy summarisation. The summary preserves *what tables exist* and *what the analysis is about*, but loses the specific constraints the user established (fiscal year definition, priority exclusions). This is actionable: it points to exactly what the compression summary needs to include more explicitly.

## Running the Full Pipeline

```bash
# 1. Run a session
pnpm run:qwery-default -- --db tpch --type dcs --indices 1

# 2. Extract inline metrics report
pnpm extract

# 3. Run the quality judge (requires DB + GEMINI_API_KEY)
pnpm verify:consistency \
  --result data/results/qwery-default/plain/tpch/dcs/tpch-dcs-001.json \
  --connection-string postgres://postgres:postgres@localhost:55432/tpch \
  --sample 5 \
  --patch

# 4. Re-extract to pick up patched judge scores
pnpm extract
```
